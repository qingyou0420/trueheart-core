# TrueHeart Core 0.2 plan

- Basis: `main` at commit `9919caf` (version 0.1.2), re-verified on 2026-08-14.
- Status: **proposal**. Nothing in this document is shipped behavior. Each item
  is written so the maintainer can accept or reject it independently.
- Inputs: the point-in-time
  [0.1.0 code review](../reviews/2026-08-13-v0.1.0-code-review.md)
  (snapshot of `main` at `bda22c7`), plus a fresh re-read of current `main`
  described in section 2. Where the two disagree, section 2 wins.
- This document changes no code, no schema, no version number, and no public
  contract. The pull request that adds it must not alter production behavior.

## 1. How to use this document

Section 4 contains one decision record per open finding. Each record states
the problem as verified on 0.1.2, the invariants and tests that currently lock
the behavior, the options including "do nothing", a recommendation, the risk,
and a testable acceptance criterion. Accepting a record means authorizing that
change for a 0.2.x release; rejecting it leaves 0.1.2 behavior in place and
costs nothing elsewhere, except where a dependency is called out explicitly.

Section 5 sequences the accepted records into small releases. Section 6 lists
what 0.2 will not do regardless of which records are accepted.

Every accepted behavior change follows the repository's standing rules:

- Test-driven: a focused failing test is observed before each production
  change (`CONTRIBUTING.md`). Pure refactors instead keep the full suite green
  at every commit.
- The four quality gates pass before commit: `pytest`, `ruff check`,
  `ruff format --check`, `mypy` (strict), plus `python -m build` for releases.
- Zero runtime dependencies; no network, model, plugin, shell, vector, or
  background-worker operations in the core (`AGENTS.md`).
- Exact `Scope` for every public operation that acts on scoped data;
  `expire_raw_content` stays a whole-database maintenance operation keyed only
  by `as_of`.
- Bodies never appear in exceptions, audit rows, or tombstones; error chains
  stay `from None`; tests keep asserting both.
- Synthetic fixtures only.
- Every release walks the version interlock checklist in section 5.5.
- Push, tag, PyPI publication, and GitHub Release each require separate
  explicit authorization; this plan authorizes none of them.

Still present on 0.1.2, confirmed by reading the current source and by a
synthetic runtime probe (temporary databases, synthetic bodies only):

- **F-03 behavior.** `recall_candidates` loads every memory row and every
  lineage edge in the scope and validates each one — including recomputing the
  SHA-256 dependency fingerprint and re-deriving both deadlines — before any
  status/time/kind filtering (`sqlite.py` lines 896–985).
  `expire_raw_content` selects from `raw_events` with no WHERE clause and
  validates every receipt in every tenant (lines 987–1055). `audit` loads all
  audit rows in the scope and sorts and truncates in Python; the existing
  `idx_audit_scope_time` index is not used for an SQL-side
  `ORDER BY … LIMIT` (lines 1098–1130). Measured scaling (one scope, one
  memory per event, warm file-backed database):

  | Rows in scope | `recall(limit=20)` | `audit(limit=100)` | `expire_raw_content` |
  | --- | --- | --- | --- |
  | 500 | 18 ms | 15 ms | 15 ms |
  | 2,000 | 69 ms | 66 ms | 60 ms |
  | 8,000 | 281 ms | 227 ms | 232 ms |

  Growth is linear in stored rows, not in the returned `limit`; at 10⁵ rows a
  single call extrapolates to seconds. A corrupt row in one tenant was
  confirmed to make whole-database `expire_raw_content` raise
  `RepositoryCorruption`; the whole-scope recall failure is locked by existing
  tests.
- **F-04 behavior.** `TrueHeart.audit` accepts `limit` 1–100 with no
  pagination (`service.py` lines 100–109). `occurred_at` is caller-claimed:
  materialize stores `MemoryDraft.created_at`, governance stores
  `GovernanceCommand.occurred_at`, expire stores the supplied `as_of`, ingest
  stores the service clock. Same-timestamp ties are broken by `audit_id`,
  a random `uuid4`. Rows older than the newest 100 are unreachable through
  the public API.
- **F-06 refactor.** `sqlite.py` is 1,687 of 2,435 source lines (69%);
  `service.py` is 109. Lifecycle transitions (`_govern_memory`), trust ceiling
  and retention derivation (lines 675–686), idempotency equality
  (`_is_identical`, `_is_identical_memory`), tombstone semantics
  (`_find_tombstones`, `_tombstone_identity`, `_insert_tombstone`),
  audit policy (`_AUDIT_POLICY`, `_audit_record`), integrity validation
  (`_memory_record`, `_receipt`, `_lineage_fingerprint`), and missing-entity
  precedence (`_raise_missing_entity`) all live inside the adapter. The
  `Repository` protocol (`ports.py`) is operation-level. Since 0.1.2 the
  documentation states this honestly, so this is debt reduction, not a doc
  fix.
- **F-07.** The legacy `memory_sources` migration is still present
  (`_LEGACY_MEMORY_SOURCES_SCHEMA` lines 98–112,
  `_migrate_legacy_memory_sources` lines 367–417, called from
  `_initialize_schema` on both fresh and existing databases). Git history
  shows the legacy five-column shape existed only between unpublished
  commits `266385d` and `faf8672` (both 2026-08-13, both before the `v0.1.0`
  tag); the migration itself arrived in `29ee0ac`, also pre-tag. No published
  release ever created the legacy shape. The migration does not increment
  `SCHEMA_VERSION`, so schema version 1 currently describes two physical
  shapes.
- **F-08.3.** `MemoryDraft.source_event_ids` and `RecallQuery.kinds` have no
  length cap (`domain.py` lines 161–167 and 280–283). The probe confirmed
  both constructors accept 100,000-element tuples on 0.1.2. These are the
  last unbounded public inputs; content, metadata, string components, and
  `limit` are all bounded.

## 3. Constraints that bind every item

Restated once so individual records can reference them:

1. **Validate-before-filter is a contract, not an accident.** Tests such as
   `test_recall_rejects_corrupt_status_or_deadline_before_eligibility_filtering`
   and `test_recall_validates_corrupt_kind_before_optional_kind_filter`
   require recall to detect a corrupt row even when eligibility filtering
   would discard it. `docs/security-guarantees.md` ("Read paths validate
   persisted rows before they filter or truncate. This is intentional…")
   promises the same. Any SQL-side filter pushdown is a contract change that
   needs explicit maintainer acceptance and coordinated doc + test changes.
2. **SQL statement shapes are pinned.** `test_recall_uses_one_read_snapshot_and_batch_loads_lineage`
   and `test_empty_recall_checks_schema_without_right_join` assert recall
   uses exactly one transaction and exactly two SELECTs of a specific shape.
   Changes to read SQL must renegotiate these tests deliberately, not
   incidentally.
3. **Body-free everywhere.** Dozens of tests assert sentinel bodies never
   appear in exceptions or persisted governance rows and that
   `error.value.__cause__ is None`. New code paths must preserve both.
4. **Idempotency is exact equality.** Replays must match every canonical
   field (`test_each_changed_canonical_ingest_field_conflicts`,
   `test_identical_materialization_uses_creation_snapshots_not_current_sources`).
5. **Schema version is checked inside every transaction.**
   `test_every_repository_transaction_requires_exact_schema_v1` and friends
   pin fail-closed behavior for missing/extra/wrongly-typed version rows.

## 4. Decision records

### D-1 (from F-07) — remove the never-published legacy lineage migration

**Problem.** Every `SQLiteRepository` construction runs a migration branch
for a `memory_sources` shape that no published release can have produced
(evidence in section 2). It permanently complicates `_initialize_schema`,
and it makes schema version 1 ambiguous: two physical shapes share one
version number, contrary to the otherwise strict versioning discipline
(`_require_supported_schema` fails closed on any other deviation).

**Locked today by:** `test_legacy_v1_lineage_is_atomically_migrated_and_remains_recallable`
and `test_legacy_v1_lineage_migration_failure_rolls_back_original_table`
(`tests/test_materialize.py`), plus the `_replace_lineage_with_legacy_v1`
fixture helper.

**Options.**

1. Do nothing.
2. Keep the migration and add a comment/doc note recording that it exists
   only for databases created from unpublished 2026-08-13 development
   checkouts.
3. Remove `_LEGACY_MEMORY_SOURCES_SCHEMA`, `_migrate_legacy_memory_sources`,
   the migration call sites, and the two migration tests; add one focused
   test that a legacy-shape database now fails closed with a body-free
   `RepositoryCorruption`.

**Recommendation: option 3.** No PyPI artifact ever wrote the legacy shape,
so removal cannot affect a user of a published version. It deletes a
permanently-running init branch and restores "one version, one shape".
Option 2 is the acceptable fallback if the maintainer knows of a private
database created from those specific unpublished commits.

**Risk.** Low. Only a database created from an unpublished dev checkout in
the 2026-08-13 window becomes unusable (fail-closed, body-free) instead of
being silently migrated. Note the observable failure point moves: repository
construction succeeds (the `CREATE TABLE IF NOT EXISTS` statements no-op),
and the first operation touching the missing snapshot columns raises
`RepositoryCorruption` via the existing sqlite-error translation. If the
maintainer prefers failing at construction, an explicit shape check can be
kept — that is a smaller version of option 2 and should be decided when the
RED test is written.

**Acceptance criteria.** Migration constants, methods, call sites, and the
two migration tests are gone. A new test builds a legacy-shape fixture
database (reusing the current helper's SQL) and proves operations fail closed
with `RepositoryCorruption`, body-free, `__cause__ is None` (RED first: on
0.1.2 the same fixture migrates successfully). Fresh databases and databases
created by any published 0.1.x are unaffected. All gates green.

### D-2 (from F-08.3) — bound `MemoryDraft.source_event_ids` and `RecallQuery.kinds`

**Problem.** These are the last unbounded public inputs. A host bug (or a
hostile caller upstream of the host's own validation) can pass a
100,000-element tuple: validation walks it, the dependency-fingerprint
canonical JSON grows with it, `materialize_once` then issues one source
lookup per event ID inside a single write transaction, and an oversized
`kinds` tuple is scanned per candidate row during recall filtering. All
other inputs are bounded (256 KiB content, 16 KiB metadata, 128-char
components, 64 depth, 4096-bit integers, `limit` ≤ 100).

**Locked today by:** nothing to unlock — no test asserts huge tuples are
accepted. `_validate_source_event_ids` already requires a non-empty,
duplicate-free tuple of ≤128-char strings; `RecallQuery` already validates
each kind string.

**Options.**

1. Do nothing; the host owns input hygiene.
2. Cap both: reject with field-named, body-free `ValidationError` above the
   cap. Proposed constants, consistent with the existing power-of-two limits:
   `source_event_ids` ≤ 128 entries, `kinds` ≤ 32 entries. The exact numbers
   are a maintainer choice; the decision here is that caps exist.
3. Cap only `source_event_ids` (the write-path amplifier), leave `kinds`
   unbounded.

**Recommendation: option 2.** It matches the project's "validated and
bounded" guarantee wording, and the caps are far above plausible legitimate
use (a memory derived from more than 128 events can be represented by
consolidating events at the host).

**Risk.** This is a tightening contract change: input that 0.1.x accepted
will raise `ValidationError`. Must be called out in the changelog and README.
A host that genuinely needs wider fan-in must restructure before upgrading.

**Acceptance criteria.** RED tests first, mirroring the existing boundary
tests: exactly-at-cap accepted, cap-plus-one rejected, for both fields;
error message names only the field and rule. README (limits paragraph in
Security boundaries) and `docs/security-guarantees.md` (metadata/limits
section) updated in the same change. All gates green.

### D-3 (from F-04) — audit pagination as an additive API

**Problem.** Audit rows accumulate forever, but the public API returns only
the newest `limit` (≤100) records by claimed time. Older records are
reachable only by bypassing the library and reading SQLite directly, which
forfeits validation and the body-free projection.

**Locked today by:**
`test_audit_is_exact_scope_stable_newest_first_and_validates_limit`
(limit bounds including `True` rejection, newest-first order, cross-call
stability) and the audit corruption tests (whole-scope validation).

**Options.**

1. Do nothing; hosts that need history read SQLite directly at their own
   risk (status quo, documented).
2. Keyset pagination: `audit(scope, *, limit=100, before=None)` where
   `before` is a previously returned `AuditRecord`; the call returns the
   newest `limit` records strictly older than the anchor in the existing
   `(occurred_at DESC, audit_id DESC)` order. `before=None` keeps today's
   behavior exactly. The anchor must belong to the requested scope, else
   `ValidationError`.
3. Time-range filtering (`since`/`until` datetimes) instead of a cursor.

**Recommendation: option 2.** It is additive (keyword-only, default
preserves current behavior), deterministic under the existing sort key, and
makes every audit row reachable through the validated public projection.
Option 3 composes worse with same-timestamp runs (caller-claimed times mean
duplicates are common) — a cursor with the `audit_id` tie-break paginates
through ties correctly, a pure time filter cannot.

Two boundaries stay explicit:

- **This does not change validation cost.** Each page still validates every
  audit row in the scope before slicing (constraint 1 in section 3). Cost
  per page remains O(scope rows). Making page cost O(limit) requires D-5.
- **This does not strengthen ordering.** `occurred_at` stays caller-claimed
  and ties stay `uuid4`-ordered; pagination proves reachability, not order
  (see D-4). Pages can shift if a caller inserts rows claiming timestamps
  inside an already-read range; documentation must say so.

**Risk.** Public API surface grows (one keyword parameter — no new exported
symbol, `__all__` unchanged). Semantics around equal timestamps must be
tested precisely or the cursor will skip or repeat rows.

**Acceptance criteria.** RED tests on a fixed synthetic timeline containing
same-timestamp runs longer than `limit`: walking pages with `before` visits
every record exactly once, in the same order a single large read would give;
`before=None` is byte-identical to 0.1.2 behavior; a wrong-scope or
non-`AuditRecord` anchor raises `ValidationError`; corrupt rows anywhere in
the scope still fail the call body-free. Existing ordering test unmodified.
README audit bullet and `docs/security-guarantees.md` audit paragraph gain
the pagination sentence and keep the caller-claimed-time warning. All gates
green.

### D-4 (from F-04) — reliable audit ordering (schema change; default: defer)

**Problem.** Same-timestamp audit records are ordered by random `uuid4`, and
`occurred_at` is caller-claimed, so the API deliberately "proves occurrence,
not order" (documented since 0.1.1). If the maintainer wants the audit
projection to reflect true write order, that needs storage support.

**Options.**

1. Keep the documented weakness (do nothing).
2. Order ties by SQLite's implicit `rowid`. Rejected even if D-4 is wanted:
   `audit_log` has a TEXT primary key, so its implicit rowid is not durable —
   `VACUUM` may renumber it — and host-run maintenance must not silently
   reorder audit history.
3. Schema version 2: add a monotonic insert sequence column (assigned inside
   the write transaction), break ties by sequence, optionally also store an
   adapter-written `recorded_at`. Requires the first real schema migration,
   version-gate updates (`SCHEMA_VERSION`, `_require_supported_schema`,
   recall's in-snapshot version check), and a decision about whether the
   sequence or `recorded_at` becomes visible on the public `AuditRecord`
   (visible fields are a public API change; an internal-only sort key is
   not).

**Recommendation: option 1 for 0.2** — the weakness is documented, D-3 does
not depend on fixing it, and option 3 is the first change that would make
schema version 2 exist, which deserves its own carefully sequenced release.
If the maintainer does want it, do it as the last 0.2 slice, after D-1 has
removed the legacy special case (one version : one shape before adding
version 2), and write the migration tests first.

**Risk (option 3).** First-ever schema migration on published databases;
any error is a user-data risk. Interaction with the recall read path's
version check and with `_requires_fresh_schema` must be re-tested for both
v1→v2 upgrade and fresh-v2 paths.

**Acceptance criteria (option 3, if accepted).** Migration tests prove: v1
databases upgrade atomically with rollback on failure; fresh databases are
created at v2; v2 databases fail closed under a v1-only library
(forward-compatibility check); ties order by insertion even across equal
claimed timestamps; existing audit tests updated deliberately, not
incidentally.

### D-5 (from F-03) — audit read pushdown (contract change; default: do not)

**Problem.** `audit` validates every row in the scope per call even though
the schema already has `idx_audit_scope_time`. An SQL-side
`ORDER BY occurred_at DESC, audit_id DESC LIMIT ?` would bound the loaded
set to `limit` rows (stored timestamps are canonical fixed-width UTC text,
enforced on write and re-checked on read, so lexicographic text order equals
chronological order, and the `audit_id` tie-break is the same lexicographic
comparison Python performs today).

**But** this stops validating rows outside the returned window: a corrupt
older row would no longer make `audit` unavailable. That contradicts the
documented promise that read paths validate before they truncate
(constraint 1), and weakens corruption detection in exchange for
availability and speed. It is exactly the trade the 0.1.x docs chose to
document rather than make.

**Options.**

1. Do nothing: whole-scope validation stays; cost stays O(scope rows);
   corruption anywhere in the scope stays loud.
2. Push `ORDER BY … LIMIT` (and the `before` anchor from D-3, if accepted)
   into SQL; validate only loaded rows; update both security documents and
   the threat model row to say corruption detection covers only the rows a
   call actually returns.

**Recommendation: option 1 for 0.2.** The documented DoS surface is real but
bounded (audit is per-scope, unlike expire), the probe shows costs are
tolerable at realistic scope sizes, and silent non-detection of old-row
corruption is a worse default for an audit surface than loud unavailability.
Revisit if a real host reports audit-scope sizes where O(scope) reads hurt.
If accepted anyway, ship it in the same slice as D-3 so audit read semantics
change once, not twice.

**Risk (option 2).** Availability improves but integrity reporting narrows;
documentation must be updated in lockstep or the security docs become false.
Existing audit corruption tests corrupt all rows and would still pass —
new tests must pin the narrowed contract explicitly (old corrupt row no
longer fails the call; corrupt row inside the window still does).

**Acceptance criteria (option 2, if accepted).** New tests as above, an SQL
trace test pinning the pushed-down statement shape, both security documents
and README updated, changelog behavior callout. All gates green.

### D-6 (from F-03) — recall and expire full scans: keep, and say so

**Problem.** Recall cost grows with scope size and expire cost with database
size (numbers in section 2); one corrupt row fails the whole scope (recall)
or the whole database (expire).

**Why this is not simply a bug:** validate-before-filter is the integrity
contract (constraint 1), the recall SQL shape is pinned (constraint 2), and
recall's full-scan validation includes cross-row invariants (fingerprint
recomputation against lineage edges, deadline re-derivation against source
snapshots) that cannot move into SQL without abandoning the contract.
`expire_raw_content` is defined as whole-database maintenance; adding a
scope filter would change its public meaning (F-05 settled that wording in
0.1.1).

**Options.**

1. Do nothing in 0.2. The consequences are documented since 0.1.1; hosts
   with modest per-scope row counts (≤ a few thousand) see tens of
   milliseconds per call.
2. Design an incremental-validation scheme (per-row validation cache keyed
   by row content hash, or a persisted integrity ledger). Real design work
   with schema impact; premature while no host has reported the ceiling.
3. Add a separate maintenance/integrity-sweep API so hosts can detect
   corruption proactively on their own schedule instead of at recall time.
   Additive public API; does not reduce per-call cost.

**Recommendation: option 1 for 0.2.** Record option 2 as the standing 0.3
candidate design topic, to be started only when a concrete host workload
justifies it. Option 3 only if the maintainer actively wants an operational
tool now; otherwise it is API surface without a requester.

**Acceptance criteria (option 1).** None — no change. The item stays on the
books; this record is the "do nothing, deliberately" documentation.

### D-7 (from F-06) — extract policy from the SQLite adapter

**Problem.** Nearly all domain policy lives inside `sqlite.py` (inventory in
section 2). A second adapter today means reimplementing lifecycle
transitions, trust ceiling, retention derivation, idempotency equality,
tombstone semantics, audit policy, and every projection validator — with
only the contract tests as a net. The 1,687-line adapter is also where most
review attention concentrates.

**Locked today by:** the entire behavioral suite (248 tests), which pins
error precedence (for example tombstone-before-existence checks in
`_raise_missing_entity`), body-free properties, SQL statement shapes
(constraint 2), and transactional rollback behavior.

**Options.**

1. Do nothing until a second adapter is actually scheduled.
2. Full re-architecture: make `Repository` a persistence-primitive protocol
   and move transactions and policy into the service. Rejected: transaction
   ownership belongs with the storage engine (`BEGIN IMMEDIATE`, rollback
   semantics, WAL retries are SQLite-specific), and the diff would be close
   to a rewrite of the file the tests trust most.
3. Extract storage-independent policy into an internal, underscore-private
   module (for example `_policy.py`): pure functions and tables for
   lifecycle transition validity, trust ceiling, retention deadline
   derivation, idempotency equality, audit action/entity/reason policy,
   tombstone matching, and the projection invariant checks that
   `_memory_record` / `_receipt` / `_lineage_fingerprint` apply after row
   loading. The adapter keeps SQL, transactions, and row mapping, and calls
   the shared functions. The `Repository` protocol and public API do not
   change.
4. Option 3 plus parametrizing the behavioral tests over a repository
   factory fixture, so a future adapter runs the identical contract suite
   unchanged.

**Recommendation: option 3, with option 4 as a cheap follow-on.** It converts
"second adapter = full rewrite" into "second adapter = SQL + transactions",
shrinks the high-risk file, and is invisible to users. Option 1 is a
defensible YAGNI position; the counterargument is that the extraction also
pays off for review and maintenance of the existing adapter, not only for a
hypothetical second one.

**Risk.** Behavior-preserving refactors can still drift on error precedence
or exception classification. Mitigations: no public API diff, no schema
diff, no SQL shape diff; refactor lands as a series of small commits with
the full unmodified suite green after each (the suite, not the diff, is the
arbiter); no RED phase is required because no behavior changes
(`CONTRIBUTING.md` reserves RED/GREEN for behavior changes and allows
refactoring "only while the focused and full suites remain green").

**Acceptance criteria.** Zero edits to existing tests in the refactor
commits (new unit tests for the extracted module are welcome additions);
`__all__` unchanged; schema unchanged; the policy inventory listed in
section 2 imports from the internal module instead of being defined in
`sqlite.py`; `sqlite.py` drops materially in size; all gates green. If
option 4 is included: the suite runs against a factory fixture defaulting to
`SQLiteRepository`, with zero behavioral edits.

## 5. Proposed release slices

Prefer several small releases over one big bang. Each slice is independently
shippable and separately abandonable; all of them are ordinary 0.2.x
releases. **Do not start any slice until its decision record is accepted.**

### 5.1 Slice A → 0.2.0 (contract tightening, no schema change)

- D-1: remove the legacy lineage migration.
- D-2: cap `source_event_ids` and `kinds`.
- Both are small, behavior-tightening, fail-closed changes with no new API.
- **Public behavior changes:** yes — previously-accepted inputs/databases now
  fail closed (changelog callouts required).

### 5.2 Slice B → 0.2.1 (additive audit pagination)

- D-3: `before` keyset pagination on `audit`.
- **Public API change:** yes — additive keyword-only parameter; no new
  exported symbol; `before=None` preserves 0.2.0 behavior exactly.
- Independent of Slice A; can ship first if preferred, but keeping the
  tightening slice first gives hosts one clean upgrade order.

### 5.3 Slice C → 0.2.2 (internal policy extraction)

- D-7: extract policy into an internal module (option 3, then option 4).
- **Public behavior changes:** none. Riskiest diff of the three, which is
  why it ships alone, after the behavior slices, on a stable base.

### 5.4 Conditional slice D → 0.2.3+ (only if explicitly accepted)

- D-5 (audit read pushdown) and/or D-4 option 3 (schema v2 with a monotonic
  audit sequence). Both are contract or schema changes this plan recommends
  **against** doing by default. If both are accepted they belong together
  (one audit-semantics change, one schema bump). D-1 must land first so
  schema v2 is not built on top of the legacy special case.

### 5.5 Version interlock checklist (every slice)

Versions and artifact names are intentionally hardcoded and fail-loud. Each
release must update, together:

- `pyproject.toml` `version`.
- `scripts/verify_release_artifacts.py` wheel/sdist/dist-info names.
- `.github/workflows/release.yml` tag guard and artifact filenames (three
  places).
- `.github/workflows/ci.yml` reinstall-wheel filename.
- `tests/test_release_artifacts.py` names and synthetic fixture versions.
- `tests/test_public_api_and_example.py`: the pyproject version assertion and
  the assertion that `docs/security-guarantees.md` opens with the current
  version.
- `README.md` Purpose/Installation/Status version references;
  `docs/architecture.md`, `docs/security-guarantees.md`,
  `docs/threat-model.md` version intros; `CHANGELOG.md`; `SECURITY.md`
  supported-versions line ("latest 0.1.x" becomes stale at 0.2.0).

Tag, GitHub Release, and PyPI publication remain separately authorized and
are not part of any slice.

## 6. What 0.2 will not do

Regardless of which records are accepted, 0.2 will not add or change:

- Semantic search, embeddings, vector storage, or ranking beyond the
  existing deterministic clarity/recency/ID ordering.
- Model, network, plugin, shell, or background-worker operations in the
  core; no schedulers (expiry stays host-called).
- Encryption at rest, key management, or protection against a malicious
  local administrator or compromised host.
- Authentication, authorization, or any multi-tenant service layer; `Scope`
  stays caller-supplied database isolation.
- Provider-side deletion, backup/snapshot management, or cryptographic
  erasure claims.
- New runtime dependencies (the list stays empty), new supported adapters
  (D-7 is groundwork only), or an async API.
