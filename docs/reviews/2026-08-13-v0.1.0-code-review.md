### F-01（P2）缺失 `py.typed`，下游用户拿不到任何类型信息

- **位置**：`src/trueheart_core/`（无 `py.typed` 文件）；`pyproject.toml`（无 package-data 声明）
- **证据**：安装本包后，在下游项目运行：

  ```console
  printf 'from trueheart_core import Scope\ns = Scope("t", "o", "s")\nreveal_type(s)\n' > check.py
  python -m mypy --strict check.py
  ```

  输出：`error: Skipping analyzing "trueheart_core": module is installed, but missing library stubs or py.typed marker`，`Revealed type is "Any"`。
- **影响**：库内部 mypy strict 全过，但缺少 PEP 561 标记，所有公开契约类型对用户退化为 `Any`，与"显式契约"的项目定位直接冲突。
- **建议修复**：
  1. 新增空文件 `src/trueheart_core/py.typed`；
  2. 在 `pyproject.toml` 增加：

     ```toml
     [tool.setuptools.package-data]
     trueheart_core = ["py.typed"]
     ```

  3. 用 `python -m build` 构建后确认 wheel 与 sdist 都包含 `trueheart_core/py.typed`。
- **验收标准**：上面的下游 mypy 实验通过且 `reveal_type` 显示 `Scope`；`scripts/verify_release_artifacts.py dist` 依旧通过（该脚本校验 RECORD 覆盖与哈希，不做文件白名单，加文件不破坏它）；四件套通过。
- **严重级别说明**：这是打包/类型消费问题，不影响运行时正确性或安全性；且向已发布的 0.1.0 补文件不可能（PyPI 不可变），修复必然落在下一个版本号。按本报告的级别定义（P2 = 应在 0.1.x 修复）定为 P2：**下一个次版本（如 0.1.1）必须包含**，不构成"立即修复"级别。
- **注意**：此修复需同步执行第五节版本号互锁清单。

### F-02（P2）瞬态写锁竞争被报告为 `RepositoryCorruption`

- **位置**：`src/trueheart_core/sqlite.py` 各公开方法的异常翻译分支（`except sqlite3.Error: ... raise RepositoryCorruption(...)`，如 `ingest_event` 约 528–531 行、`govern` 约 1060–1063 行）；`_connect` 中 `PRAGMA busy_timeout = 5000`（约 245 行）
- **证据**：另开一个连接执行 `BEGIN IMMEDIATE` 占住写锁后调用 `ingest_event`，5 秒 busy 超时后收到 `RepositoryCorruption: event ingest failed`。复现脚本要点：

  ```python
  blocker = sqlite3.connect(path, isolation_level=None)
  blocker.execute("PRAGMA journal_mode = WAL")
  blocker.execute("BEGIN IMMEDIATE")
  blocker.execute("INSERT INTO schema_migrations (version, applied_at) VALUES (99, 'x')")
  service.ingest_event(draft)  # 5s 后 RepositoryCorruption
  ```

- **影响**：宿主无法区分"数据库损坏（应停机排查）"与"另一写者正忙（应重试）"，两者的正确应对相反。多进程宿主会把正常竞争当成损坏。`_enable_wal` 已有针对 `SQLITE_BUSY`/`SQLITE_LOCKED` 的指数退避重试（约 257–280 行），说明作者意识到该问题，但普通操作路径没有同等处理。
- **建议修复**（二选一，倾向 a）：
  - (a) 新增公开异常 `RepositoryBusy(TrueHeartError)`：在异常翻译处检查 `sqlite3.OperationalError.sqlite_errorcode` 的低 8 位是否为 `SQLITE_BUSY`/`SQLITE_LOCKED`（参考 `_enable_wal` 现有判别逻辑），是则抛 `RepositoryBusy`，否则维持 `RepositoryCorruption`。消息保持 body-free、`from None`。同时导出到 `__init__.py`、更新 README 错误列表。
  - (b) 在适配器内对 busy/locked 做有界重试（复用 `_enable_wal` 的退避模式），耗尽后仍抛与现状一致的错误。
- **验收标准**：新增测试用占锁连接复现（注意：`busy_timeout` 值 5000 是硬编码，测试会等 5 秒；建议将其提为模块级常量以便测试替换，或接受 5 秒的单测耗时）；断言异常类型、body-free、`__cause__ is None`；现有 240 个测试不回归。
- **注意**：这是公开 API 扩展（新异常类型），需更新 `tests/test_public_api_and_example.py` 中的 `PUBLIC_NAMES`/`PUBLIC_SYMBOLS`、README 的稳定导入列表。

### F-03（P3，维护者决策）读路径全量扫描：规模天花板与"一行损坏即全 scope 不可用"

- **位置**：
  - `recall_candidates`（`sqlite.py` 约 875–964 行）：无条件加载 scope 内全部 `memories` 与全部 `memory_sources`，逐条在 Python 里重算 SHA-256 依赖指纹、重推期限，再做状态/时间/kind 过滤与排序；
  - `expire_raw_content`（约 966–1032 行）：`SELECT ... FROM raw_events` 无 WHERE，扫描**所有租户**全部行并校验每一张收据；
  - `audit`（约 1072–1104 行）：加载 scope 全部审计行后在 Python 排序截断，未用已建索引 `idx_audit_scope_time` 做 SQL 侧 `ORDER BY ... LIMIT`。
- **证据**：2000 条记忆的 scope 上 `recall(limit=20)` 约 60ms、`audit(limit=100)` 约 53ms，随总量线性增长（外推 10 万条约 3 秒/次）。任何一行损坏使整个 scope 的 recall 失败；任何一个租户的一行损坏使全库 expire 失败。
- **重要约束（勿盲改）**：现有测试**有意要求**"先校验后过滤"，例如 `test_recall_rejects_corrupt_status_or_deadline_before_eligibility_filtering`（`tests/test_recall.py`）要求即使该行会被资格过滤剔除也必须先发现损坏。把过滤下推到 SQL 会改变完整性契约并使这些测试失败。**这是设计权衡，不是随手可修的 bug。**
- **建议**（按侵入性递增）：
  1. 最低限度：在 `docs/security-guarantees.md` 或 README 明确写出可用性后果——"scope 内任何一行损坏 → 该 scope recall 整体不可用；任一租户损坏 → 全库 expire 不可用"（当前威胁模型只笼统提到 DoS 残留风险）；
  2. `audit` 可以在**不放弃校验**的前提下用 SQL `ORDER BY occurred_at DESC, audit_id DESC LIMIT ?` 缩小加载集——但这意味着不再校验老行，同样是契约变更，需要维护者确认；
  3. 长期：为 0.2 设计增量校验（如按行哈希缓存校验结果）或提供独立的完整性巡检/修复工具。
- **验收标准**（若只做文档项）：文档新增措辞与实现一致；不改代码则无测试变更。

### F-04（P3）审计 API 只能取最近 100 条，且时间线由调用方控制

- **位置**：`service.py` `audit`（约 100–109 行，`limit` 上限 100，无分页参数）；`sqlite.py` `_insert_materialize_audit`（约 768–786 行，`occurred_at` 取调用方的 `draft.created_at`）、`_insert_governance_audit`（约 1513–1533 行，取 `command.occurred_at`）、`audit` 排序（约 1085–1087 行，`occurred_at` 降序，uuid4 的 `audit_id` 降序决胜）
- **影响**：
  1. 审计日志无限增长，但公开 API 永远只能看到按声称时间排序的最新 100 条，更早记录只能绕过公开 API 直读 SQLite；
  2. `occurred_at` 是调用方声称的时间（materialize 用 `created_at`、governance 用 `command.occurred_at`），且相同时间戳下用随机 uuid4 决胜，与真实写入顺序无关——审计能证明"发生过什么"，不能可靠证明"顺序"。
- **建议修复**：
  - 短期（文档）：在 README/`docs/security-guarantees.md` 明确"审计时间为调用方声称时间；API 仅返回最近 `limit` 条"；
  - 0.2（行为）：审计排序决胜改用单调 `rowid`（真实插入序）；增加分页（如 `before` 游标）或时间范围过滤。两者都是公开行为变更，先写测试。
- **验收标准**（文档项）：措辞与实现一致。（行为项）新增测试覆盖同时间戳顺序稳定性与分页边界；现有 `test_audit_is_exact_scope_stable_newest_first_and_validates_limit` 不回归。

### F-05（P2）README/AGENTS/安全文档的 Scope 保证与 `expire_raw_content` 签名不符

- **位置**：同一保证出现在**四处**——`README.md` Guarantees 首条（"Every public operation uses an exact caller-supplied `Scope` ..."，约 15–16 行）；`AGENTS.md` 全局约束第 3 条；`docs/security-guarantees.md` "Enforced by the core" 首条（约 8–9 行："Every public operation requires an exact caller-supplied `Scope` ..."）；`docs/threat-model.md` "Scope confusion" 一行（约 13 行："Every operation requires exact `Scope(tenant_id, owner_id, subject_id)` ..."）。实际签名 `service.py` 约 86–88 行：`expire_raw_content(*, as_of)` **不接受 scope**，作用于全库所有租户（见 F-03 的扫描证据）

- **验收标准**：四处措辞一致且与实现相符；`tests/test_public_api_and_example.py` 对 README 的断言只覆盖 five-minute 一节，不受影响；四件套通过。
- **注意**：`AGENTS.md` 同句约束也建议同步修改，否则后续贡献者会再次困惑。

### F-08（P4）次要问题合集

1. **无 `__version__` 属性**：包内无版本属性（`tests/test_release_artifacts.py` 的合成 wheel 夹具反而带 `__version__`）。建议在 `__init__.py` 用 `importlib.metadata.version` 暴露或明确不提供。
2. **`_normalize_datetime` 异常捕获过窄**：`domain.py` 约 59–69 行只捕获 `OSError/OverflowError/TypeError/ValueError`；敌意 `tzinfo` 抛 `RuntimeError` 等会原样穿透而非包装为 `ValidationError`（仍 fail-closed，但异常类型契约不稳定）。建议**小幅扩大白名单而非改为裸捕 `Exception`**：例如在现有元组中加入 `RuntimeError`（或维护一个小的显式异常白名单），保持 `from None` 防泄漏。裸捕 `Exception` 会把本库自身的实现 bug 也吞成 `ValidationError`，掩盖真实缺陷，不建议。
3. **无界元组入口**：`MemoryDraft.source_event_ids` 与 `RecallQuery.kinds` 长度无上限（内容/元数据有字节上限，这两个没有）。若加上限（如 source_event_ids ≤ 某常量）属公开契约变更，先写测试并更新文档。
4. **CI 矩阵止于 Python 3.13**：`.github/workflows/ci.yml`。以 2026-08 时点建议加入 3.14。
5. **无 Dependabot/Renovate 配置**：Actions 均按 SHA 固定，但没有自动跟进更新；威胁模型自己写了 "maintainers can ... let pins age"。建议加 `.github/dependabot.yml`（`package-ecosystem: github-actions`）。
6. **`release.yml` 硬编码 `v0.1.0`**：每次发版必须手改 tag 校验、wheel/sdist 文件名（同见第五节）。这是有意的 fail-loud 设计，接受即可，但应写入发版操作文档。

## 四、明确不建议"修复"的有意设计（避免过度修改）

以下各项看起来不寻常，但均为经过测试锁定的有意设计，**除非维护者明确要求，不要改动**：

1. **拒绝 `:memory:` 路径**（`sqlite.py` 约 228–229 行）：连接每操作新建，内存库会各自独立，拒绝是正确的。
2. **治理 `reason` 不落库**（`_insert_tombstone`/`_insert_governance_audit` 固定写 `"governance requested"`）：防调用方把正文塞进 reason，属 body-free 不变量。
3. **幂等重放要求逐字段全等**（`_is_identical`/`_is_identical_memory`），差异一律 `IdempotencyConflict`。
4. **每次读取全量重算指纹并校验不变量**、"先校验后过滤"：完整性优先于性能的既定契约（详见 F-03 的约束说明）。
5. **确定性时钟注入**（`TrueHeart(clock=...)`）与召回排序三级键（clarity ↓、created_at ↓、memory_id ↑）。
6. **`ScopeMismatch` 的一位存在性泄露**：已在 README/安全文档明确披露并要求宿主授权 ID 使用，是文档化权衡。
7. **异常链一律 `from None`**：防止 sqlite 原始错误消息（可能含正文片段）通过 `__cause__` 泄漏；测试大量断言此点。
